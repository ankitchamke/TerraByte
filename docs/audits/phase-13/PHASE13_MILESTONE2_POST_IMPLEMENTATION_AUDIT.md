### 2.3 Detailed Investigation of Migration Edits

The file `supabase/migrations/20261106160000_phase13_database_foundations.sql` was modified during Milestone 2 to resolve critical DAC/RLS gaps that would have caused immediate runtime permission errors on the frontend:

```sql
-- Diff Line 893: Added remove_facility_member RPC
CREATE OR REPLACE FUNCTION public.remove_facility_member(
  p_facility_id UUID,
  p_technician_profile_id UUID
) ...

-- Diff Line 2017: Granted table-level INSERT/UPDATE on repair_facilities
GRANT INSERT, UPDATE ON TABLE public.repair_facilities TO authenticated;

-- Diff Line 2067: Granted table-level UPDATE/DELETE on facility_memberships
GRANT SELECT, UPDATE, DELETE ON TABLE public.facility_memberships TO authenticated;

-- Diff Line 2101: Added facility_memberships_delete_policy
CREATE POLICY "facility_memberships_delete_policy" ON public.facility_memberships ...
```

#### Why these migration edits were strictly necessary:
1. **`GRANT INSERT, UPDATE ON TABLE public.repair_facilities TO authenticated`**:
   - In Milestone 1, line 1947 ran `REVOKE ALL ON TABLE public.repair_facilities FROM anon, PUBLIC;` and only granted column-level `SELECT`.
   - In PostgreSQL, even if `repair_facilities_insert_policy` and `repair_facilities_update_policy` exist, missing table-level DML privileges causes PostgreSQL to halt with `42501 permission denied for table repair_facilities` before evaluating RLS.
   - Without this grant, technician workshop registration (`RegisterWorkshopDialog`) and facility attribute updates (`ManageWorkshopDialog`) fail unconditionally.
2. **`GRANT SELECT, UPDATE, DELETE ON TABLE public.facility_memberships TO authenticated`**:
   - Milestone 1 only granted `SELECT` to `authenticated`. Without `UPDATE` and `DELETE`, no member could be removed or resign.
3. **`facility_memberships_delete_policy` & `remove_facility_member` RPC**:
   - The approved Phase 13 specification explicitly required:
     > *"OWNER can remove any active member (except self). MANAGER can remove TECHNICIAN members only. Demoting or deleting the OWNER membership directly is blocked by trg_guard_owner_membership_mutation."*
   - Milestone 1 omitted both the DELETE policy and a removal RPC on `facility_memberships`. Adding `remove_facility_member` as a `SECURITY DEFINER` routine satisfies this contract safely.

#### Migration History Invariant Assessment:
Because migration `20261106160000_phase13_database_foundations.sql` has **never been applied** to remote Staging (`ubqgvhcfmrvnmrbllcom`) or Production (`hwdrypkvszwrcraujctw`), maintaining these necessary DAC grants in the foundation migration preserves a clean, unfragmented schema without breaking remote environments. All 36 database invariant tests continue to pass (36/36).

### 6.2 Defects Discovered & Remediated During Validation
1. **`guard_owner_membership_mutation` Fallthrough Deletion Bug**:
   - **Root Cause**: The BEFORE DELETE/INSERT/UPDATE trigger function `guard_owner_membership_mutation()` checked `IF TG_OP = 'DELETE' AND OLD.role = 'OWNER'` to block owner deletions. However, for non-owner deletions (such as regular TECHNICIAN or MANAGER members), execution fell through to the function's terminal `RETURN NEW;`.
   - In PostgreSQL triggers on `DELETE`, `NEW` is `NULL`. When a BEFORE DELETE trigger returns `NULL`, PostgreSQL cancels the deletion operation for that row. Consequently, any attempt to delete a regular member (directly or via `remove_facility_member` RPC) deleted 0 rows.
   - **Remediation**: Updated `guard_owner_membership_mutation()` to check `IF TG_OP = 'DELETE' THEN ... RETURN OLD; END IF;`, ensuring non-owner deletions return `OLD` and proceed successfully.
2. **Table Grant Hardening on `repair_facilities` and `facility_memberships`**:
   - **Root Cause**: Table creation previously inherited default privileges for role `authenticated`, granting unwanted permissions (such as `TRUNCATE` or `DELETE` on facilities).
   - **Remediation**: Added explicit `REVOKE ALL ON TABLE public.repair_facilities FROM anon, authenticated, PUBLIC;` and `REVOKE ALL ON TABLE public.facility_memberships FROM anon, authenticated, PUBLIC;` prior to granting only the safe, required DML privileges (`INSERT, UPDATE` on facilities; `SELECT, UPDATE, DELETE` on memberships).
